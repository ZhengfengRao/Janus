## 1. 产品一句话定义

> Janus 是 macOS 上的全能受托 Agent。用户给出目标、约束、授权和风险预算，Janus 自主理解、计划、操作现有 App 并完成任务；当行动超出授权范围、风险预算、验证能力或责任边界时，Janus 升级确认或安全停下。

更完整地说：

> Janus 是把现有软件转化为可调用能力节点的全能受托 Agent。用户可以在任意数字工作现场唤起 Janus，把跨软件的数字目标委托给它；Janus 负责理解目标、制定路径、检查自主策略、执行已授权步骤、验证结果、汇报完成情况，并通过 Delegation Center 治理长期授权、风险预算、记忆、审计和恢复。

Janus 不是普通 AI 助手，不是桌面聊天框，不是单 App 插件，也不是试图替代微信、飞书、邮箱、浏览器或文件系统的超级 App。它位于用户和软件之间，把现有软件转化为用户目标可以调用的能力节点。

```text
用户 → Janus → 各种软件
```

最高权力归属不变，但执行模型从“关键动作都由人确认”升级为“关键动作由授权策略决定”：

```text
目标由人给出；
授权由人授予；
风险预算由人治理；
路径由 Agent 处理；
授权范围内自主执行；
超出授权、风险预算或责任边界时升级确认；
过程必须可见；
权力必须可撤回。
```

## 2. 产品要解决的真实问题

表层问题是用户每天在多个软件之间重复打开、搜索、切换、复制、粘贴、整理、创建草稿、上传下载、发送例行同步、维护日程和记忆流程。

深层问题是：

> 现代软件把人变成了界面劳动者，而用户真正想要的是结果，不是亲自走完每一步界面路径。

Janus 的正当性不是“替代人”，而是：

> 把机械性还给机器，把目的、判断、身份与责任还给人；把已授权的数字行动交给 Agent，把超界判断还给用户。

产品问题定义：

```text
如何让用户表达数字目标、约束、授权和可接受风险，让 Janus 在用户定义的权限和风险预算内跨 App 完成任务，并在需要新的判断、身份承担、责任确认或风险超界时升级确认、接管或安全停下。
```

这要求 Janus 不只交付“低风险草稿准备”，而是以完成为默认志向；同时通过授权、风险预算、可见性、中断、验证、复盘、记忆治理和信任恢复，让更高自主性长期可信。

## 3. 用户与使用场景

Janus 面向被软件流程消耗、希望把数字目标委托出去的 macOS 用户。早期核心用户是高频跨软件工作者：知识工作者、沟通密集型用户、项目管理与协作用户、创作者与研究者、普通大众用户。

Janus 不按 App 划分用户，而按委托成熟度划分：

| 用户阶段 | 心智 | 典型需求 | 产品重点 |
|---|---|---|---|
| 初次助手用户 | 想知道它能不能帮我 | 打开 App、找文件、创建草稿、整理材料 | 快速入口、低风险任务、明确边界 |
| 授权操作用户 | 愿意让它完成已授权动作 | 预填、整理、更新文档、可撤销本地动作 | Janus Surface、自主策略、单步验证、可接管 |
| 重复委托用户 | 愿意给固定规则 | 例行汇报、周期整理、固定对象同步 | Standing Authorization、风险预算、恢复能力 |
| 高自主性用户 | 愿意给更大目标和预算 | 跨 App 多步目标、外部可见例行动作 | 风险预算、升级策略、审计和信任反馈 |
| 治理用户 | 关心长期信任 | 管理权限、记忆、审计、能力边界 | Delegation Center、撤销、恢复、组织策略 |

核心 JTBD：

```text
当我有一个数字目标时，
我希望表达结果、约束和可接受风险，
让 Janus 在授权范围内跨 App 完成任务，
只在需要新的判断、授权或责任承担时问我，
这样我可以获得结果，而不是被界面劳动消耗。
```

## 4. 产品原则

| 原则 | 产品规则 |
|---|---|
| 用户主权 | Janus 必须保护目的主权、判断主权、身份主权、责任主权。 |
| 授权内自主优先 | 已被授权、可验证、在风险预算内的动作应由 Janus 自主完成，而不是反复打断用户。 |
| 完成而非准备是默认志向 | Janus 的长期目标是完成电脑任务；准备 / 草稿是早期验证切片和特定授权状态，不是产品上限。 |
| 风险预算是产品对象 | 风险预算必须可表达、可查看、可撤销、可审计，可约束对象、动作、频率、金额、外部影响和期限。 |
| 能力不是权力 | Capability ≠ Permission ≠ Necessity ≠ Executability。能打开、点击、输入、读取，不等于有权这样做。 |
| 当前上下文是线索，不是边界 | 当前 App / Window / 选中对象可帮助理解任务，但任务边界由用户目标、授权、风险预算和验证共同决定。 |
| 单步行动，单步验证 | Janus 的内部纪律是 `行动 → 验证 → 再行动`；证据验证不能被模型置信度替代。 |
| 安全停下不是失败 | 遇到不确定、验证不足、用户中断、边界冲突或风险预算不足时，正确行为是 Safely Stopped / Escalated。 |
| Learning Candidate ≠ Memory | 可发现学习候选，但不能静默保存长期记忆。 |
| Memory ≠ Permission | 保存记忆不能扩大行动权限；授权行动不能自动保存记忆。 |
| 一次确认 ≠ 长期授权 | 单次确认只对当前动作或当前任务有效，长期授权必须在 Delegation Center 明确治理。 |
| 外部影响必须被授权覆盖 | 发送、提交、上传、发布、审批、支付、权限变更等外部影响动作必须被一次性确认、standing authorization 或风险预算策略覆盖；未覆盖则升级确认或停下。 |
| 授权控制基础设施使高自主性成立 | 停止、接管、恢复、审计、撤销不是降低自动化的阻碍，而是让更高自动化可信的基础。 |

## 5. 产品总体结构

Janus 只有三个 canonical 产品表面：

```text
Janus Entry / Janus 入口
Janus Surface / Janus 主行动面
Delegation Center / 受托关系中心
```

| 表面 | 解决的问题 | 不承载 |
|---|---|---|
| Janus Entry | 如何随时把一个目标交给 Janus，并在任务中停止、恢复或聚焦当前任务 | 完整任务解释、长期治理、复杂设置 |
| Janus Surface | 如何完成一次受托任务：理解、计划、自主策略 / 风险预算检查、执行、验证、升级确认、停下、复盘 | 跨任务权限/记忆治理 |
| Delegation Center | 如何长期治理委托任务、授权、风险预算、standing authorization、记忆、审计和信任恢复 | 当前任务的主要确认流 |

### 5.1 Janus Entry

Janus Entry 是用户在任意 macOS 工作现场发起或恢复 Janus 的入口。它必须：

- 随时可达，但不随时观察；
- 低存在感，但任务中可见；
- 能发起任务，也能停止、暂停、恢复或聚焦当前任务；
- 可基于当前上下文，但不被当前上下文限制；
- 采用单一任务胶囊，支持可编辑输入、提交和长按语音。

长按语音是最高频 fast path：用户长按 Janus Entry 或语音按钮开始采集，松开结束并提交 Intent；Janus Surface 承接任务。对象明确、授权覆盖、可验证、在风险预算内的任务，可直接推进到完成或等待升级确认状态。理解、计划、自主策略、风险预算判断、步骤验证和审计仍必须存在，只是可默认折叠进行动轨迹。

### 5.2 Janus Surface

Janus Surface 是一次受托任务的核心协作界面，是同一受托行动界面在不同生命周期中的状态容器。

它承载：目标理解、Plan 或 Action Trace、自主策略 / 风险预算、授权与风险、执行状态、验证结果、阻塞与升级确认、中断与接管、完成复盘、学习候选。

核心叙事：

```text
我理解了什么；
我准备怎么做；
我被授权做什么；
当前风险预算覆盖什么；
我不会做什么；
我正在做什么；
我为什么可以继续；
我为什么必须升级或停下；
我已经做了什么；
我没有做什么。
```

### 5.3 Delegation Center

Delegation Center 是治理 Janus 行动权的空间，不是传统设置页，也不是长期并行任务后台。

它回答：我把什么交给了 Janus、Janus 可以自动做什么、Janus 必须问我什么、哪些 standing authorization 正在生效、风险预算如何限制自主执行、Janus 记住了什么、Janus 曾经做过什么、Janus 哪里失败过以及如何恢复信任。

一级模块：

1. **托管**：当前任务 + 可展开历史任务的串行账本；
2. **授权**：跨任务授权规则治理，覆盖自动执行、发送前确认、禁止执行、一次性授权、standing authorization、撤销和过期；
3. **风险预算**：治理对象、动作、频率、金额、外部影响、期限、升级策略和违规记录；
4. **记忆**：跨任务记忆治理，覆盖已保存偏好、联系人线索、App 习惯和待确认候选。

审计、信任恢复和能力降级作为任务行、授权行、风险预算行和记忆行背后的可展开证据与治理能力，不堆叠为更多 canonical 产品表面。

## 6. 核心任务生命周期设计

完整生命周期：

```text
Intent Capture
→ Understanding
→ Planning
→ Autonomy Policy / Risk Budget Check
→ Ready / Auto-start / Escalate
→ Authorized Executing
→ Verifying
→ Auto-complete / Blocked / Confirming
→ Completed / Safely Stopped / Failed
→ Review & Learning Candidate
```

面向用户可压缩为：

```text
表达目标 → 理解目标 → 展示计划 → 声明授权与风险预算 → 授权内执行与验证 → 完成或升级确认 → 复盘与学习
```

| 阶段 | 产品规则 |
|---|---|
| 表达目标 | 捕获原始指令、入口、当前环境、目标环境、目标对象、显式限制、外部影响、确认偏好和风险预算线索。 |
| 理解目标 | 形成可审查理解；清晰且授权覆盖的任务可折叠展示，但内部纪律不能省略。 |
| Plan / Action Trace | 计划必须存在于任务模型和审计证据中；清晰链路可不作为执行前阻塞步骤。 |
| Autonomy Policy / Risk Budget Check | 判断每个 Step 是否被一次性授权、standing authorization 或风险预算覆盖；未覆盖则升级或停下。 |
| 授权执行与验证 | 每个 Step 执行后进入 Verifying；没有验证信号，不继续自动执行。 |
| Auto-complete | 全部步骤在授权和风险预算内完成且验证通过时，可直接完成并汇报。 |
| 阻塞、升级确认与接管 | 多候选、对象不确定、外部影响未授权、删除/覆盖/上传/权限修改未覆盖、登录/验证码/支付/审批、用户暂停/停止/接管、验证不足、路径偏离都必须升级确认或安全停下。 |
| 完成、失败与复盘 | 记录已做、未做、授权依据、风险预算消耗、是否产生外部影响；Safely Stopped、Failed、Completed 必须区分。 |

用户对当前任务始终拥有停止、暂停、接管、修改、恢复、撤销、复盘权。

## 7. 授权、风险预算与升级确认产品规则

### 7.1 自主性 / 风险等级

| 等级 | 名称 | 示例 | 产品策略 |
|---|---|---|---|
| L0 | 观察 / 建议 | 识别当前窗口、读取选中对象 | 显示采集范围，可关闭 |
| L1 | 协助 / 准备 | 打开 App、切换窗口、搜索、起草 | 可自动执行，需可见、可验证 |
| L2 | 可撤销自动完成 | 保存副本、整理文件、更新本地草稿 | 授权覆盖时可自动完成，需恢复路径 |
| L3 | 授权重复执行 | 固定例行汇报、周期整理、固定对象同步 | 需要 standing authorization，受频率、对象、期限约束 |
| L4 | 风险预算内自主执行 | 对固定群发例行同步、更新有版本历史的共享文档 | 需要明确风险预算与升级策略 |
| L5 | 高利害边界 | 支付、审批、权限变更、不可逆删除、法律/组织承诺 | 默认升级确认或硬停；只有明确授权 / 组织策略覆盖时才可执行 |

L4/L5 不是静态“永远不能自动”，但必须有匹配的授权、风险预算、验证和升级策略；否则不得继续。

### 7.2 R 类风险事件

R 类风险事件是一票否决事件，必须拦截、降级、升级确认或禁止：未经授权发送/提交/发布/审批；用户停止、暂停或接管后仍继续执行；静默保存敏感记忆；一次确认泛化为长期授权；用模型置信度替代验证信号；任务外持续观察；把 Recovery、Blocked、Safely Stopped 伪装为 Completed；风险预算违规。

### 7.3 授权表达

授权类型：一次性授权、条件授权、standing authorization、风险预算策略、禁止规则。

授权必须具体到 App、对象、动作、风险等级、有效范围、期限、撤销路径和升级策略。例如：

```text
允许 Janus 每个工作日 18:00 前向固定项目群发送例行进度摘要；
摘要只能来自指定项目文档和今日任务记录；
不得承诺客户交付日期；
遇到客户承诺、金额、合同、权限变更或不确定事实时必须问我。
```

### 7.4 确认卡 / 升级卡

高风险或超界升级卡必须包含：动作类型、目标对象、目标环境、即将产生的外部影响、是否可撤销、授权是否覆盖、风险预算是否足够、Janus 已经做了什么、Janus 还没有做什么、用户可选项（确认一次、修改、授予规则、接管、取消）。

## 8. 记忆、学习与个性化产品规则

| 规则 | 说明 |
|---|---|
| 学习不是默认发生 | Janus 可以识别 Learning Candidate，但必须由用户决定是否保存。 |
| 记忆必须可治理 | Delegation Center 提供查看、来源、编辑、撤销、作用范围和使用历史。 |
| 记忆类型有限 | 用户偏好、对象映射、环境知识、流程偏好、禁止偏好。 |
| 记忆不产生权限 | 记住“张三是谁”不等于允许自动给张三发消息。 |
| 权限不产生记忆 | 允许本次发送前创建草稿，不等于保存联系人映射或组织信息。 |
| 候选项不等于事实 | Learning Candidate 在用户确认前只能作为本次任务线索。 |

记忆提示必须提供至少三个选择：仅本次使用、记住、不要再提示。

## 9. 核心界面摘要

详细状态、布局、文案和组件规范属于 `janus-product-experience-design.md`。本文只保留产品结构摘要。

### 9.1 Janus Entry 摘要

默认形态是单一任务胶囊：

```text
[J]  你想让 Janus 完成什么？  [按住说话] [↵]
```

任务中可变为状态胶囊或进入 Janus Surface 执行态，支持暂停、停止、接管、恢复、查看行动轨迹。

### 9.2 Janus Surface 摘要

Janus Surface 动态呈现目标摘要、当前理解、Plan / Action Trace、授权与风险预算、当前步骤、验证结果、停下原因或升级确认卡、时间线、学习候选。不同阶段动态显示，不应一次性堆满。

### 9.3 Delegation Center 摘要

```text
Delegation Center
├── 托管：当前任务 + 历史任务
├── 授权：自动执行 / 发送前确认 / 禁止执行 / 一次性授权 / standing authorization / 已撤销授权
├── 风险预算：对象 / 动作 / 频率 / 外部影响 / 期限 / 升级策略 / 违规记录
└── 记忆：已保存偏好 / 联系人线索 / App 习惯 / 待确认学习项 / 已删除或已忽略记忆
```

串行托管是前提：当前任务只能有一个；历史任务用于查看和复盘，不用于恢复长期并行委托。

## 10. 典型用户旅程摘要

详细 journey、状态和 copy 属于 `janus-product-experience-design.md`。本文只保留验证产品模型的代表性场景。

| 场景 | 验证点 |
|---|---|
| 准备明天客户会 | 用户表达结果、约束和风险预算；Janus 跨 App 整理文件、更新文档、处理日程，并对客户承诺升级确认。 |
| 授权发送例行项目同步 | standing authorization 覆盖固定对象、模板和频率；未覆盖内容必须升级。 |
| 跨 App 创建微信消息草稿 | 当前上下文是线索，任务边界来自目标、授权、风险预算和验证；微信只是代表性外部消息场景。 |
| 查找并打开飞书文档 | Janus 替用户处理路径，但不替用户判断最终正确对象。 |
| 选中文件后创建邮件草稿 | 对象入口降低表达成本，但不降低外部影响授权标准。 |
| 安全停下与信任恢复 | 停下不是失败；多候选、验证不足和风险预算不足时必须给出选择、接管和复盘。 |

微信、邮件、评论、表单提交、上传和审批都只是外部可见动作的代表类型。Janus 的通用对象是目标、环境、对象、动作、授权、风险预算、验证和结果。

## 11. 产品文案与信任表达规范

| 类别 | 规则 |
|---|---|
| 文案原则 | 明确而不拟人过度；解释授权和风险预算而不制造恐惧；承认不确定而不显得无能；汇报行动而不掩盖未做事项；请求升级确认而不转移责任。 |
| 推荐句式 | “我理解你想……”“当前授权允许我……”“这个动作在风险预算内……”“我需要升级确认……”“我不会做……”“已验证……”“我已经做了……”“我没有做……”。 |
| 禁止句式 | “放心交给我”但不说明边界；“我认为可以发送”替代授权；“以后我都这样做”但没有授权范围；“我记住了”但没有用户授权；把安全停下说成失败或完成。 |

## 12. 产品与技术运行时映射

| 产品机制 | 技术对象 / 模块 | 产品要求 |
|---|---|---|
| 用户输入目标 | Intent | 保留原始表达和显式限制 |
| 一次委托任务 | Task | 所有行动必须绑定 Task |
| 当前与目标环境 | Context / EnvironmentRef | 当前上下文是线索，不是边界 |
| 行动计划 | Plan | 可解释、可修改、可审计 |
| 单步动作 | Step / Action | Step 是最小可执行单位 |
| 自主策略 | AutonomyPolicy / PolicyDecision | 决定自动执行、升级确认、停下或降级 |
| 授权边界 | PermissionGrant / StandingAuthorization / DelegationRule | 授权可查看、可撤销、有范围和期限 |
| 风险预算 | RiskBudget / EscalationPolicy | 风险预算是可治理对象，违规目标为 0 |
| 确认 / 升级卡 | ConfirmationPayload / EscalationPayload | 超界动作前必须说明对象、影响、授权和风险预算 |
| 执行状态 | ExecutableStep / Task State | 执行后必须验证 |
| 验证结果 | VerificationRequirement / VerificationEvent | 模型置信度不是验证信号 |
| 中断接管 | InterruptToken | 用户中断最高优先级 |
| 恢复计划 | RecoveryPlan / RecoveryRecord | 失败、停下、接管后提供可理解恢复路径 |
| 审计时间线 | AuditEvent / Timeline | 记录已做、未做、授权依据和风险预算消耗 |
| 学习候选 | LearningCandidate | 不自动保存为 Memory |
| 长期记忆 | Memory | 明确授权、可撤销、可审计 |

## 13. 研发衔接与产品验证门

研发路线遵循：

```text
Evidence-first Native Runtime
证据优先的本地桌面运行时路线
```

顺序：先建立 Task / Step / AutonomyPolicy / Permission / RiskBudget / Verification / Audit 运行纪律，再接入 macOS 控制能力，再接入模型理解和规划能力，最后扩展 App 能力、记忆能力、并发能力和第三方扩展能力。

| Gate | 名称 | 产品通过标准 |
|---|---|---|
| Gate 0 | 总纲一致性门 | 功能能追溯到全能受托 Agent，不破坏用户主权 |
| Gate 1 | Runtime 骨架门 | 产品界面能表达 Task、Step、AutonomyPolicy、Permission、RiskBudget、Verification、Audit |
| Gate 2 | 低风险即时执行门 | 低风险动作可见、可中断、可验证，可完成受控跨 App 路径 |
| Gate 3 | 授权重复 / 可撤销执行门 | standing authorization 覆盖的任务可无逐步确认完成，并可恢复、撤销、审计 |
| Gate 4 | 外部影响授权执行门 | 外部可见动作可在明确授权和风险预算内执行；超界升级；风险预算违规为 0 |
| Gate 5 | 复杂多步自主目标门 | 多 App、多对象、多约束目标可在授权范围内完成，遇到责任或风险边界升级 |

派生 PRD 必须说明：用户问题、生命周期阶段、自主等级、风险预算、授权类型、验证信号、审计内容、安全停下 / 升级条件、不做什么、与三大产品表面的关系、对 Gate 0-5 的影响。

## 14. 产品成功指标

Janus 的成功首先看是否显著减少界面劳动、提高授权范围内的电脑任务完成率，并让用户在自动执行之后仍然信任系统；确认、停下、复盘和恢复都是支撑高速委托可信持续的指标。

| 指标 | 含义 |
|---|---|
| 界面劳动减少率 | 用户是否少切换、少查找、少复制粘贴、少记流程 |
| 授权内自主任务完成率 | 在授权和风险预算覆盖范围内，Janus 是否能完整完成任务 |
| 可准备 / 可完成结果到达时间 | 从表达目标到完成、可检查结果或等待升级确认状态的时间 |
| 避免不必要确认数 | 已授权、可验证、低风险动作是否不再反复打断用户 |
| 重复流程复用率 | 用户是否愿意把同类任务交给 Janus 重复处理 |
| 外部影响越权率 | 未授权发送、提交、删除、权限变更等必须为 0 |
| 风险预算违规数 | 超预算执行、超范围执行、未记录消耗目标为 0 |
| 用户接管成功率 | 用户能否随时接管并理解状态 |
| 验证信号覆盖率 | Step 是否有可靠验证依据 |
| 成功恢复率 | 失败、停下或接管后是否能恢复到安全、可理解状态 |
| 自动执行后信任度 | 用户是否理解自动执行依据，并愿意继续授权 |
| 复盘可理解度 | 用户能否理解已做、未做、授权依据和风险预算消耗 |
| 授权撤销成功率 | 撤销后是否立即生效 |
| 记忆误保存率 | 未授权记忆保存必须为 0 |

反指标：自动执行步数越多越好、覆盖 App 越多越好、模型回答越自然越好、用户确认越少越好、后台主动性越强越好。若这些指标破坏用户主权、授权边界、可见性、验证或复盘，应降级。

## 15. 产品反模式清单

| 反模式 | 禁止原因 |
|---|---|
| 聊天框化 | 把 Janus 做成只会回答问题的桌面 Chatbot。 |
| 启动器化 | 把 Janus 做成只负责打开 App 或搜索入口的 launcher。 |
| 插件化 | 把 Janus 降级为单 App 插件，失去全能受托 Agent 的跨 App 目标完成能力。 |
| 超级 App 化 | 试图替代微信、飞书、邮箱、浏览器或文件系统。 |
| 脚本化 | 把能力固化为逐 App、逐场景脚本。 |
| 黑箱自动化 | 执行过程不可见、不可中断、不可复盘。 |
| 效率至上 | 为了少确认而越过授权、风险预算或责任边界。 |
| 确认崇拜 | 对已授权、可验证、在风险预算内的动作反复确认，削弱 Agent 完成任务的价值。 |
| 拟人越权 | 让 Janus 像用户本人一样承诺、拒绝、道歉或发送。 |
| 后台监控 | 把 Janus Entry 误做成长期观察系统。 |
| 静默学习 | 未经授权保存联系人、路径、偏好、组织信息。 |
| 一次确认泛化 | 把单次授权推导为长期权限。 |
| 风险预算虚设 | 文案上声称有预算，执行时无法约束或审计。 |
| 模型置信替代验证 | 用“AI 觉得成功”替代证据。 |
| 完成伪装 | 把 Recovery、Blocked、Safely Stopped 说成 Completed。 |

## 17. 最终产品判断

Janus 的完整产品形态不是：

```text
一个只会控制电脑的 AI；
一个跨 App 自动化脚本集合；
一个桌面聊天助手；
一个替代所有软件的超级 App；
一个无人管理、把模型置信当权力的黑箱 Agent。
```

Janus 的完整产品形态是：

```text
一个以用户目标为起点，
以任务生命周期为协作界面，
以自主策略、授权、风险预算、验证和审计为运行纪律，
以 Delegation Center 管理长期信任，
在 macOS 软件世界中替人完成已授权数字任务，
并在超出授权、风险预算或责任边界时升级确认的全能受托 Agent。
```

这份产品设计的最高标准不是让 Janus 显得无所不能，也不是把它压缩成只会做低风险草稿的助手；而是让它在能力增长时仍然知道边界，在授权范围内真正完成任务，在执行任务时仍然可见、可停、可查，在产生超界外部影响前仍然尊重用户责任，在学习用户习惯时仍然接受治理，在失败和不确定时仍然安全停下。
