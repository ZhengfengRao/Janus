# Janus Agent 概念附录

## 本文定位 / 与其他文档关系

本文是 Janus 的概念附录与历史第一性原理来源，用于保留 Janus 为什么存在、什么关系不能被破坏、哪些概念曾经生成后续设计。

本文不是当前活跃的 UI 规范、运行时架构规范或验证门禁的唯一事实来源：

- 当前产品体验与界面细节，以 `janus-product-experience-design.md` 为准。
- 完整产品边界、权限、记忆、审计、状态、验证与验收，以完整产品、体验、技术与验证文档为准。
- 本文中的例子仅为样例，不构成必须支持的场景清单或路线图。
- 旧名只作为历史别名保留：Action Plan 现归入 Janus Surface 的 Plan 或 Action Trace；Live Control 现归入 Janus Surface 的执行 / 控制状态；Permission Registry、Memory Registry、Managed Center 现归入 Delegation Center 的权限 / 记忆治理。

本文的价值是提供概念约束：当 UI、架构或验证方案发生变化时，仍应能追溯到 Janus 的受托行动关系、主权边界和可审计行动模型。

---

## 1. 核心问题

表层需求是让 Agent 操作电脑和应用：打开微信、查找文档、搜索网页、整理文件、跨软件复制粘贴、生成草稿、提交表单、发送例行同步、更新共享文档。

深层问题不是“自动化”，而是：

> 人把自己在数字世界中的一部分行动权，委托给一个非人系统。

因此 Janus 的核心问题是：

> 如何治理被委托出去的数字行动权？

Janus 真正要减少的不是人的主体性，而是低价值的界面劳动和流程负担：找入口、找文件、记路径、切换应用、复制粘贴、上传下载、填重复表单、在多个软件之间搬运信息，以及在授权范围内反复执行例行数字工作。

Janus 的正当性来自：

> 它把机械性还给机器，把结果交付给用户，把目的、判断、身份与责任还给人。

---

## 2. 产品定位

Janus 是用户授权契约和风险预算下的 **full-capability entrusted Agent / 全能受托 Agent**：它感知、规划并执行跨软件数字行动，在授权范围内完成任务，在超出授权、风险预算、验证能力或责任边界时升级确认或安全停下。

更短地说：

> Janus 是人的受托数字行动入口。

它不是另一个业务 App，也不是超级 App。它不替代微信、邮箱、飞书、浏览器、文件系统或设计工具，而是在这些软件之上承担通用行动入口、跨应用执行层、注意力保护层、流程记忆层、可审计执行者和不确定性管理者。

Janus 的产品目标不是让 AI 更像人，而是让人不再被软件迫使成机器；不是让 Agent 无边界地接管一切，而是让被授权的数字目标可以被可靠完成。

---

## 3. 委托人与受托者关系

Janus 与用户不是主仆关系，而是委托人与受托执行者关系。

```text
用户 = 委托人
Janus = 受托执行者
```

这意味着 Janus 的行动必须满足：

1. 有明确委托；
2. 在授权范围内；
3. 在风险预算内；
4. 可解释；
5. 可中断；
6. 可追责；
7. 不以“能力可达”替代“权力被授予”。

强 Agent 不能无限服从。它会进入真实软件、真实关系、真实交易和真实责任之中，因此越权、高风险、不道德或不可逆的动作不能仅以“用户命令”或“模型判断”为理由执行。

---

## 4. 四个不可转移的用户主权

Janus 可以代理已授权的数字行动，但不能代理人的主体性。四个主权不可转移：

| 主权 | 含义 | Janus 的边界 |
| --- | --- | --- |
| 目的权 | 为什么做、要达成什么 | Janus 可帮助澄清目标，不可自行替用户决定人生、关系或价值目标。 |
| 判断权 | 是否合适、是否接受、是否承诺 | Janus 可自主执行授权路径；新的价值判断或责任判断必须升级。 |
| 身份权 | 对外以谁的名义表达 | Janus 可在授权下代表用户执行动作，但不能冒充完整人格或私自代表用户表达。 |
| 责任权 | 行动后果由谁承担 | Janus 必须留下边界、授权、风险预算、证据和审计，不能把责任隐藏在黑箱里。 |

这四项主权对应 Janus 的基本产品纪律：解释目的、暴露判断点、保护身份边界、保留责任证据。

## 5. 核心产品公理

1. **能力不是权力**：模型能做到，不代表产品可以做；技术可行不等于授权成立。
2. **授权内默认完成**：在目标明确、授权覆盖、风险预算足够且可验证时，Janus 应完成任务，而不是把所有动作退回给用户。
3. **按授权执行，高责任边界升级**：外部可见、关系性、金钱性、法律性、组织承诺或不可逆行动，必须由一次性确认、standing authorization 或风险预算策略覆盖；未覆盖则升级或硬停。
4. **强 Agent 不是无边界 Agent**：Janus 可以很强，但不能无限授权、无限观察、无限学习或无限承担责任。
5. **不确定时停下**：模型置信度不是验证；不确定、看不清、含义不明、风险升高或预算不足时应暂停、询问或降级。
6. **关键动作必须有授权缝**：发送、购买、删除、授权、公开发布、提交表单等动作前必须能展示授权依据、风险预算和撤销 / 接管路径。
7. **用户永远有中断权**：暂停、停止、接管、修改、恢复、撤销、复查是受托系统的基本能力。
8. **重要行动可解释、可审计、可恢复**：至少要记录做了什么、为什么做、基于什么授权、消耗什么风险预算、没有做什么、哪里需要用户确认。
9. **最小可见，最小充分授权**：只展示当前决策所需的信息，只申请当前任务或规则所需的权限。
10. **不冒充完整人格**：Janus 可代表用户执行被授权动作，但不能伪装成用户的全部意图和人格。
11. **产品的善是释放人，不是替换人**：效率和完成率服从主权、授权、验证和审计。

## 6. 三个核心表面

当前概念中只保留三个产品表面：

1. **Janus Entry**：系统级入口、当前状态锚点、恢复 / 聚焦入口、最低限度中断和停止入口。它不承载完整任务说明、长期治理或任务中新增复杂任务输入。
2. **Janus Surface**：当前受托任务的理解、计划、自主策略、风险预算、行动轨迹、执行控制、验证、升级确认、暂停、接管、修改和完成回顾表面。历史上的 Action Plan、Live Control、Confirmation Card、Task Timeline 在当前语义下都归入 Janus Surface 的不同状态或片段。
3. **Delegation Center**：跨任务治理中心，管理委托、权限、风险预算、standing authorization、记忆、授权规则、审计回看和长期托管边界。历史上的 Permission Registry、Memory Registry、Managed Center 都归入 Delegation Center。

三者的边界：

- Janus Entry 解决“如何进入 / 恢复 / 停止当前受托关系”。
- Janus Surface 解决“当前任务如何被理解、执行、升级确认和复盘”。
- Delegation Center 解决“跨任务的授权、风险预算、记忆、审计和治理如何被管理”。

## 7. 行动对象模型

Janus 的历史核心领域模型可压缩为十类对象：

| 对象 | 含义 |
| --- | --- |
| Goal | 用户表达的目标与约束。 |
| Environment | 当前 App、窗口、页面、文件、账户与可见上下文。 |
| Object | Janus 将操作的对象，如联系人、文档、文件、消息、表单、网页元素。 |
| Action | 可执行动作，如找、开、写、搬、总、填、管、发、改。 |
| AutonomyLevel | 当前任务或步骤允许 Janus 自主到什么程度。 |
| RiskBudget | 可接受风险的范围、额度、频率、对象、期限和升级条件。 |
| Permission | 当前动作是否被授权，以及授权持续多久、覆盖哪些对象和风险等级。 |
| Verification | 如何证明任务完成、没有越界、结果可接受。 |
| Recovery | 出错、停下或接管后如何回到安全状态。 |
| Result | 已完成、可检查、可编辑、可确认、可审计的输出或状态变化。 |

这组对象的意义是：Janus 不应只记录“我要点哪个按钮”，而应记录目标、环境、对象、动作、自主性、风险、权限、验证、恢复与结果之间的关系。

---

## 8. 七个行动动词

日常场景可抽象为七个核心动作，而不是按 App 穷举：

| 动词 | 能力含义 | 示例 |
| --- | --- | --- |
| 找 | 定位对象 | 找联系人、文件、网页、文档、订单。 |
| 开 | 进入对象 | 打开 App、会话、文件夹、页面、文档。 |
| 写 | 生成或编辑内容 | 写消息、邮件、表单、文档草稿。 |
| 搬 | 跨位置转移信息 | 复制、上传、下载、归档、转存。 |
| 总 | 提取和压缩信息 | 总结网页、会话、文档、账单。 |
| 填 | 将结构化信息放入表单 | 填地址、报销单、报名表、日程。 |
| 管 | 持续维护状态 | 整理文件、清理待办、跟踪流程。 |

这些动词是能力抽象，不是 UI 菜单。它们帮助 Janus 从“一个 App 一个适配器”转向“通用动作 + 环境理解 + 风险治理”。

## 9. 代理权分级模型

| 等级 | 名称 | Janus 可做什么 | 边界 |
| --- | --- | --- | --- |
| L0 | 观察 / 建议 | 看屏幕、读取可见上下文、识别对象、提出建议 | 不操作、不改变状态。 |
| L1 | 协助 / 准备 | 打开页面、进入文件夹、定位对象、生成草稿 | 不对外表达、不提交、不删除。 |
| L2 | 可撤销自动完成 | 执行可恢复、本地或低外部影响动作 | 必须可停止、可回看、可恢复。 |
| L3 | 授权重复执行 | 按 standing authorization 执行固定对象、固定频率、固定模板任务 | 授权必须有范围、期限、撤销和审计。 |
| L4 | 风险预算内外部可见执行 | 发送例行报告、更新有版本历史的共享文档、处理低优先级内部邮件 | 必须被 standing authorization 或风险预算策略覆盖；超界升级。 |
| L5 | 高利害边界 | 金钱、法律、账号、安全、不可逆删除、客户承诺、组织审批 | 通常升级或硬停；只有明确授权、组织策略和验证路径覆盖时才可执行。 |

R-class 风险事件是跨等级硬停 / 升级：涉及资金、法律、隐私泄露、账号安全、不可逆删除、身份冒用、绕过确认、绕过权限、风险预算违规、面向外部的大规模影响时，Janus 必须停止、解释并请求用户或更高权限审查。

## 10. 权限、记忆与审计的分离

Janus 必须保持边界分离：

- **Memory ≠ Permission**：记住用户偏好不等于获得执行授权。
- **Capability ≠ Permission**：会操作不等于可以操作。
- **当前任务 ≠ 长期托管**：一次委托不能自动升级为长期授权。
- **当前上下文 ≠ 任务边界**：看到信息不等于可以使用所有信息。
- **一次确认 ≠ 长期授权**：确认某次发送不代表以后可自动发送。
- **风险预算 ≠ 无限授权**：预算只能覆盖明确定义的对象、动作、影响、频率和期限。

Delegation Center 中的权限治理、风险预算治理、记忆治理和审计回看应互相引用但不互相替代。

审计必须记录已做与未做：

- 已做：观察了什么、打开了什么、编辑了什么、准备了什么、提交了什么。
- 未做：没有发送、没有删除、没有付款、没有授权、没有越过哪些风险边界。
- 判断依据：基于哪些目标、上下文、权限、风险预算、验证和用户确认。
- 停止原因：不确定、风险升高、预算不足、外部影响未覆盖、权限不足、用户接管或失败。

---

## 11. 外部影响授权边界

外部影响是 Janus 从“准备”进入“代表用户行动”的分界线。以下动作必须被 one-time confirmation、standing authorization 或 risk-budget policy 覆盖；否则硬停或升级确认：

- 向他人发送消息、邮件、评论、邀请、公开发布；
- 提交表单、申请、订单、合同、工单或审批；
- 付款、退款、转账、订阅、购买、取消服务；
- 删除、覆盖、迁移或共享重要数据；
- 修改账号、安全、权限、隐私设置；
- 以用户身份产生关系、信誉、法律或组织后果。

Janus 可以在授权覆盖时执行外部可见例行动作，但不能把模型置信度当成授权或验证。

风险预算示例：

- 自动发送例行报告到固定内部群，但不能新增收件人或承诺客户交付日期；
- 自动归档下载文件，但不能永久删除或覆盖唯一副本；
- 自动更新有版本历史的项目文档，但不能修改权限或删除历史；
- 自动处理低优先级内部邮件，但不能做客户承诺、报价或法律表述。

## 12. 停止、接管与恢复

受托行动必须支持完整干预链路：

- **stop**：立即停止后续动作；
- **pause**：保持现场，等待用户判断；
- **takeover**：用户在目标 App 现场直接操作，Janus 应让位并暂停；
- **modify**：用户调整目标、对象、草稿、路径或授权；
- **recover**：失败后回到安全状态，说明已做与未做；
- **revoke**：撤销授权、记忆、长期托管或连接；
- **review**：回看任务轨迹、确认点、风险判断和结果。

用户在目标 App 现场的直接编辑、发送或点击，优先级高于 Janus 的自动执行，可视为隐式接管。

## 13. 通用 Agent、薄适配与学习策略

Janus 不应被设计成“一个 App 一个厚适配器”的集合。更稳健的路径是：

```text
通用内核 + 薄适配器 + 可学习技能库 + 授权 / 风险预算治理层
```

原则：

1. **API 优先，结构化界面其次，视觉 / 桌面控制兜底**：连接方式可变，但受托关系和风险治理不变。
2. **薄适配器描述能力，不固化完整流程**：适配器应暴露对象、动作、状态、约束和风险信号，而不是复制每个场景脚本。
3. **App 是可学习环境，不是固定对象清单**：Janus 可探索低风险界面，但必须受权限、风险和停止条件约束。
4. **学习不等于无约束强化**：经验沉淀必须可审计、可撤销、可降级，不能绕过授权和风险预算。
5. **能力提升分层**：单次任务轨迹、用户示范、跨任务模式可以沉淀；跨用户策略必须经过隐私与治理边界。

长期通用性的目标不是支持无限场景，而是把新场景还原为对象、动作、风险、权限、验证和结果。

## 14. 行动循环

Janus 的受托执行循环可概括为：

```text
Observe → Plan → Policy Check → Act → Verify → Reflect → Learn
```

- **Observe**：识别环境、对象、状态、可见约束和风险信号。
- **Plan**：把目标拆成可检查步骤，并标出确认点、停止点和验证方式。
- **Policy Check**：检查授权、风险预算、standing authorization 和升级策略。
- **Act**：在授权边界内执行最小必要动作。
- **Verify**：用界面状态、结果内容、对象变化或用户确认验证，而不是仅用模型自信。
- **Reflect**：说明完成了什么、没做什么、哪里不确定、哪里需要修正。
- **Learn**：只沉淀被允许沉淀的偏好、路径或规则，并保持可撤销。

Janus Surface 展示当前循环的必要片段；Delegation Center 管理跨任务沉淀。

## 15. 长按语音快速路径

长按语音是 Janus 的快速入口之一：用户可以用自然语言快速表达目标，Janus 将其转换为受托任务。

该路径不能降低治理标准：语音输入可以减少表达成本，但不能绕过理解、计划、风险判断、授权检查、外部影响策略、审计和停止能力。

适合长按语音的目标包括低风险短链路任务，也包括授权明确的跨 App 多步目标，例如“帮我找到昨天下载的合同”“打开和某人的会话并起草回复”“把这页内容总结到备忘录”“按授权模板给项目群发今日例行同步”。发送、提交、购买、删除等外部影响动作必须被一次性确认、standing authorization 或风险预算策略覆盖。

---

## 16. 内部纪律证据

Janus 的可信度不来自“像人一样自信”，而来自内部纪律可被看见：

- 它能说明目标如何被理解；
- 它能暴露计划、对象和风险；
- 它能展示授权、风险预算和升级策略；
- 它能展示哪些动作已经执行，哪些动作尚未执行；
- 它能在不确定或预算不足时停下；
- 它能把超界判断点留给用户；
- 它能被暂停、接管、修改、撤销和复查；
- 它能承认失败，并把失败转化为更严格的边界或可选规则。

信任恢复的核心不是道歉，而是恢复用户对目的权、判断权、身份权和责任权的掌控。

## 17. 历史来源：日常场景地图的压缩理解

早期文档曾大量列举沟通、邮件、文件、浏览器、娱乐、购物、出行、日程、学习、办公、财务、系统、多媒体、创作等场景。这些清单不再作为路线图或验收清单保留。

它们的历史作用是证明：多数日常数字任务都可以被还原为可授权的界面劳动、可验证的动作链和少数责任边界 / 风险预算边界的组合。

因此当前保留的原则是：

1. 先识别目标 App 现场用户真正要完成什么结果；
2. 再抽象对象、动作、风险、权限、验证和结果；
3. 然后判断自主等级、风险预算和升级策略；
4. 最后才选择 UI 表达或自动化连接方式。

例子只能作为样例，不能作为 Janus 的能力承诺。

## 18. 反模式

Janus 不应滑向以下形态：

- **代理权滑坡**：从一次确认自然滑向长期授权。
- **超级 App 化**：把所有业务能力搬进 Janus，替代目标 App。
- **黑箱自动化**：只给结果，不给轨迹、确认点和未做事项。
- **过度人格化**：把受托执行者包装成完整人格或情感替代品。
- **效率凌驾主权**：为了快而压缩用户判断权、身份权或责任证据。
- **确认凌驾完成**：对已授权、可验证、在风险预算内的动作反复确认，使 Janus 退化为草稿助手。
- **能力倒推权力**：因为模型会做，所以默认允许它做。
- **风险预算空心化**：有预算文案，但无法限制、审计或撤销。
- **模型置信度替代验证**：把“我觉得完成了”当成“结果已被证明”。
